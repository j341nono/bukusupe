#### サンプルの「今日」を基準日に固定（2026-09-27、Claude）

星の明るさ・色・地図のタイトルの目立ち方は、最後に触れた日からの新しさ（`recency`）で決まる。これまで「今日」はページを開いた時点で、
サンプルの日時は 2026-09-26 を基準に作ってあるため、日が経つほどサンプルの星が暗くなり、中距離のタイトル（新しさ 0.55 超）も出なくなった
（前日の確認で、ドラッグ中のラベルの確認が日付のせいで 0 件になったのもこれ）。

- `src/today.ts`（`setToday` / `getToday`）を基準の今日にし、`recency()` と `brightnessOf()` の既定の「いま」をここから取る。
- main が起動時に決める：サンプルのデータ源（Web のデモ、`?sample=1`、ⓘ の切り替え、測定用の `bench` を含む）は `SAMPLE_TODAY`
  （2026-09-26 12:00 JST、`src/bookmarks/sample-source.ts`）、自分のブックマークは `Date.now()`（ページを開いた時点。今までどおり）。
- 確認：`scripts/check-today.mjs`（`check:ext` の中）。ページのスクリプトより先に Date を 400 日先へずらす差し替えを入れて読み込み直し、
  星 40 個の大きさ・明るさと、中距離で見えているタイトルの不透明度・文字の大きさを比べる。修正前はサンプルで NG（差 最大 0.77、
  タイトル 8→0 件）、修正後は差 0・8→8 件で OK。自分のブックマーク（使い捨てのプロファイルに 12 件作る）は、400 日後にすべての星が暗くなる
  （修正前後とも OK。変わらなくなっていないことの見張り）。

#### 動きがあるときだけ描く（2026-09-27、Claude）

`docs/BENCHMARK.md` の「改善の余地」への対応。何もしていない地図でも描画のループが毎コマ描いていた（画面ありの 2000 件でページ 33%・GPU 40%）。

- **仕組み**（`src/render/scene.ts`）：1 コマの終わりに `needsNextFrame()` で「このあとも描く必要があるか」を見て、要らないコマが
  `IDLE_FRAMES`（12）続いたら `setAnimationLoop(null)` で止める。要るのは：飛行中、突入の演出、カメラの移動（focus・傾き・キーの慣性・
  MapControls の減速・行列の変化）、星の動き（`StarField.isAnimating`：配置の移動・ばね・誕生・明るさと大きさの追従）、星座を描く演出、
  星座名の表示待ち、ラベルの判断待ち（`labelsDirty`・`lastLabelMotion`）、右ドラッグの傾き、`hold()` の理由（埋め込みの計算中）。
- **再開**：`wake()`。入力（pointer・wheel・key・touch を window の capture で）、画面の大きさの変化、タブが見えたとき、画面を変える公開メソッド
  すべて（`setSearch`・`setLayout`・`selectConstellation`・`enterFlight` など 23 個と、変わったときの `hoverStar`）の先頭で呼ぶ。
  止まっていた間の時間は次のコマの経過時間に数えない（`clock.getDelta()` を捨てる）。main は埋め込みの計算中に `hold("embedding")`、
  Worker の通知（進み具合・モデルの準備完了）で `wake()`。
- **星のばねの変更**：検索中は、目標に着いた星も毎コマ処理していた（ずっと「動いている」扱いになる）。目標（検索中は軌道、そうでなければ配置の
  位置）との差と速さが 0.001 未満の星は飛ばすようにした（見た目は変わらない）。
- **新しい公開**：`hold(reason, on)`、`wake()`、`isRendering`、確認用の `setContinuousRender(on)`（止めずに描く）と `renderNow()`（いまの状態で 1 コマ）。
  `setLoopPaused` は止めたままにする／動きがあるときだけ描く方式に戻す、の意味になった。
- **確認**：`scripts/check-idle.mjs`（`check:ext` の中）。修正前は 8 件 NG（何もしなくても 1.5 秒で 90 コマ）。修正後は、何もしないと 1.5 秒で 0 コマ、
  キー・ドラッグ・ホイール・検索・星座の保存・星座の選択のそれぞれで、止まった状態から 34〜157 ms で描画が再開し、落ち着くとまた止まり、
  止まった画面は描き直した画面と画素まで同じ。飛行中は操作しなくても毎コマ描き、地図へ戻ると止まる。
- **既存の確認で変えたもの**：`check-extension.mjs` の「検索中も 60 コマを保つ（3 秒平均）」は、落ち着いた検索を描き直さなくなったため、
  その 3 秒だけ `setContinuousRender(true)` で描かせて、描画の力を測る形にした。`__bukusupe.benchmark(n)` の 1.5 秒の測定も同じ。
  「計算中も画面が動いている」は `hold("embedding")` で、「保存演出中も 60 コマ」は演出そのものが動きなので、そのまま通る。
- **測定**：`npm run bench -- --only=idle`（何もしていない地図の CPU 使用率だけ。画面ありとヘッドレス）。変更前の結果は `results/idle-*-continuous.*` に残し、
  報告書は変更前後を並べる。`render-*` の場面ごとの測定は変更前のまま（動いている場面の重さは変わらない）。
- **three.js の `setAnimationLoop` を使わない**：`renderer.setAnimationLoop(null)` をコールバックの中で呼んでも、three.js は
  コールバックの後に次のコマを要求するので、止めたはずのループが空回りし、再開するたびに重なった（1 回の画面の書き換えで 2 回描き、
  確認では 60Hz で 122 回/秒）。`SpaceView` が自分で `requestAnimationFrame` を持つ（`loop`・`rafId`）。確認
  「何度止まって再開しても、描画のループが重ならない」（修正前 NG：描画 122 回・書き換え 61 回、修正後 60 回・60 回）。
- **既存の確認の修正（日付による）**：`check-extension.mjs` のドラッグ中のラベルの確認は、不透明度がちょうど 1 のラベルだけを数えていた。
  段階 2 から地図のタイトルの不透明度は「最後に触れた日」からの新しさで決まり、サンプルの日時（2026-09-26 基準）と今日の差で 1 のものが
  無くなって 0 件になった（変更前のビルドでも同じ。今回の変更とは別の原因）。見えているラベルすべて（不透明度 > 0）を数えるようにした。
- **測り直した結果**（2026-09-27 12:42〜13:06、`npm run bench -- --only=idle`）：何もしていない地図の CPU 使用率（中央値）は、画面ありの 2000 件で
  ページ 33.0%＋GPU 40.3% → ページ 0.0%＋GPU 0.0%。どの件数でも、画面あり・ヘッドレスとも 0.0〜0.1%（ループを止めたときと同じ）。
  画面ありの測定は、`Extensions.loadUnpacked` が 60 秒応答せず 2 回失敗し（同じプロファイルの Chrome を閉じた直後に起動したためとみられる。
  すぐ後に単独で起動すると 2.6 秒で読み込めた）、3 回目で完了した。
- **注意（今後）**：止まっていても動く演出（星の瞬き・星雲の揺らぎなど）を足すときは、`needsNextFrame()` にその条件を足すこと。
  足さないと、演出が止まって見える。画面を変える公開メソッドを足すときは、先頭で `this.wake()` を呼ぶこと。

#### 時間とメモリの測定（docs/BENCHMARK.md）— 完了（2026-09-27、Claude）

使う人の依頼で、製品の動作を変えずに時間とメモリのコストを測る。計画は使う人が確認済み（2 回に分けて実行：1 回目＝描画以外、
2 回目＝画面ありの描画。どちらも使う人が「始めて」と言ってから）。測定は下の「測定の結果」のとおり完了した。

- **src に足したもの（すべて `?debug=1` のときだけ動く。ふだんの動作は変えない）**
  1. 生成したブックマークの注入：`?debug=1&bench=<名前>` で、`chrome.storage.local` の `bench:<名前>` を読む（`src/bookmarks/index.ts`）。
  2. 測定用の DB：`bukusupe-bench-<名前>`（`useDataSource(kind, bench)`）。サンプルの DB を汚さない。
  3. 時間の計測点：配置の段ごと（`src/debug/timing.ts` の `timed()`。記録先が無いときは呼ぶだけ）、起動の節目（`__bukusupe.marks()`）、
     1 コマの内訳（`SpaceView.setProfiling` / `takeProfile`：全体・重ね表示・描画）。
  4. `renderer.info` の取り出し（`renderInfo()`）。
  5. Worker の WebAssembly のメモリ（Worker の名前が `bukusupe-debug` のときだけ `WebAssembly.Memory` と `instantiate` を包んで控える。`wasmMemory()`）。
  6. 描画のループの一時停止（`setLoopPaused`。何もしていないときの CPU 使用率の比較のためだけ）。
  7. 量子化の切り替え（`?debug=1&dtype=fp16|fp32`。通常は q8）。
- **スクリプト**：`scripts/bench/`（`npm run bench`、`--only=run1|run2|<項目>`、`--counts=`、`--allow-load`）。報告書は `npm run bench:report` が
  `docs/bench/results/` から `docs/BENCHMARK.md` とグラフ（`docs/bench/*.png`。SVG をヘッドレスの Chrome で PNG にする。依存は足さない）を作る。
  使い回すプロファイルは `$TMPDIR/bukusupe-bench-profile`（モデルのキャッシュと埋め込みを残す。リポジトリの外）。
- **負荷の見張り**：計画では「1 分平均のロードアベレージ 4 超で中断」だったが、試運転でロードアベレージが測定そのもの（埋め込みの計算）で 5〜7 に
  上がり、次の段が止まった。そこで判断は「このスクリプトと、それが起動した Chrome を除いたプロセスの CPU 使用率の合計が 150% 超」に変え、
  ロードアベレージは参考として記録する。
- **試運転で直したこと**：`requestAnimationFrame` の記録が前の記録に書き込む不具合（コマ数が 2 倍に見えた）／ドラッグが星のタイトル（押せる）の上から
  始まり地図が動かなかった（押し始めを canvas の上に）／キーとドラッグの場面が元の位置に戻る動きで「動いたか」を判定できなかった／
  モデルの取得は、本体の前に小さな範囲の要求（206）があるので、ファイルごとに合計する／グラフの文字化け（data URL に charset）／容量は 10 進の MB。
- **わかっている限界**：ページの時刻は 0.1 ms 刻み（それより短い処理は「< 0.1 ms」）。GPU の処理時間は測れない。WebAssembly のメモリは確保量。

**測定の結果（2026-09-27 05:30〜09:03 JST、使う人は就寝中で Mac の操作なし）**：`docs/BENCHMARK.md`（数字はすべて `docs/bench/results/` から生成）。
- 1 回目（描画以外）は 05:30〜07:25、2 回目（画面ありの描画。蓋を閉じた MacBook＋外部ディスプレイ DELL S2725DC 144Hz）は 07:27〜07:58。
- **測り直した項目**：起動の 100 件（(c) の準備完了のばらつき IQR/中央値 0.67。他のアプリの負荷が上がった時間帯。測り直すと 0.27 秒で安定）。
- **測り方を変えた項目**：メモリ。同じブラウザでページを行き来しながら測ると、前のページ（bfcache など）が同じプロセスに残り、拡張機能のページの
  プロセスが 100 件で 5.7 GB と積み上がって見えた。`scripts/bench/memory.mjs` で「測るたびにブラウザを起動し直す」方法に変えて測り直した
  （はじめの結果は `results/memory-navigating.*`）。量子化の比較の「プロセス全体」も同じ影響を受けるので使わない（WebAssembly のメモリは影響なし）。
- **飛ばした項目**：なし。
- 気になった点：量子化で int8 が fp32 より速くない（1000 件で 59.2 秒 対 57.6 秒）。何もしていない地図でも、描画のループでページ 33%・GPU 40%（2000 件、画面あり）。
