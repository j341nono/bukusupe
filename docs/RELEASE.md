## 版の番号の決まり

- 形は `メジャー.マイナー.パッチ`（Chrome の manifest の `version` は数字とドットだけなので、`-beta` などは付けない）。
- **限定公開の間は `0.9.x`**。最初の申請を `0.9.0` とし、ストアに上げ直すたびにパッチ（x）を 1 つ上げる。
  機能を足した版（段階 5 の大きな項目）はマイナーを上げず、0.9.x の中でパッチを上げる（1.0.0 までは 0.9 系で通す）。
- **一般公開で `1.0.0`**。以後は、不具合の修正だけならパッチ（1.0.1）、機能を足したらマイナー（1.1.0）、
  保存データの形が変わって移行が要るなど、利用者に影響する大きな変更はメジャー（2.0.0）を上げる。
- **3 か所を必ずそろえる**：`public/manifest.json` の `version`、`package.json` の `version`、git のタグ `vX.Y.Z`（ストアに上げたコミットに付ける）。
  段階 2 で、この 3 つが一致しないとストア向けのビルドが失敗するようにする。
- ストアは同じ番号の上げ直しを受け付けないので、上げ直すたびに必ず番号を上げる。審査で差し戻されて直した場合も上げる。
- ハッカソンの版は `0.1.0`（タグ `v0.1.0-hacksonic`）。ストアには出していない。
- 変更の記録は `CHANGELOG.md`（段階 2 で作る）に、版ごとに利用者向けの言葉で書く。

## 段階 1：安全性の調査と修正

ブックマークのタイトルと URL は、利用者のものであっても「外から来た文字列」として扱う。ストアの審査の前に、表示と遷移の経路をすべて洗う。

やること
- **表示の経路の洗い出し**：ブックマークのタイトル・URL・フォルダ名・ドメイン・星座の名前・検索語が画面に出る所をすべて一覧にし、
  すべて `textContent` などの文字列として入れていることを確かめる（HTML として解釈させない）。
  今 `innerHTML` を使っているのは `src/ui/hud.ts` の 2 か所で、中身は固定の文言と `escape()` 済みの状態の文字列だけ。これも `textContent` に置き換える。
- **特殊な URL の扱い**：星として読み込むのは `http:` / `https:` だけ（`src/bookmarks/chrome-source.ts`）。ページを開く経路（同じタブ・新しいタブ・
  `location.href`・`window.open`）の直前でも、`http:` / `https:` 以外は開かないことを二重に確かめる。`javascript:`・`data:`・`file:`・
  `chrome:`・極端に長い URL・国際化ドメイン名（見た目が紛らわしいもの）を試す。
- **極端な文字列**：非常に長いタイトル、改行や制御文字、右から左へ書く文字、絵文字、空のタイトルで、表示が崩れないこと・固まらないこと。
- **保存データ**：IndexedDB と `chrome.storage.local` に、ブックマークの内容のうち必要なもの以外を書いていないことを確かめる。
- **Web のデモ**：`location.href` で開く前の検査と、「戻る」で再開するための `sessionStorage` の内容を確かめる。
- **依存関係**：`npm audit` と、同梱している依存の版を確かめる（脆弱性があれば更新し、`THIRD_PARTY_NOTICES` を作り直す）。
- 調べた結果と直したことを、`docs/SECURITY.md`（新規）に残す。

完了条件
- [ ] 自動確認：タイトルに `<img src=x onerror=...>` や `<script>` を含むブックマークを使い捨てのプロファイルに作ると、地図・検索・カード・
      飛行中の窓・遠くの名前のどこでも文字として表示され、スクリプトが動かない（ページ内で検知用の値が書き換わらない）。
- [ ] 自動確認：`javascript:`・`data:`・`file:` のブックマークは星にならず、どの操作でも開かれない（`chrome.tabs.update` / `create` が呼ばれない）。
- [ ] 自動確認：`src/` と配布物に `innerHTML` / `outerHTML` / `insertAdjacentHTML` / `document.write` が無い（または、固定の文言だけで、理由を書いた許可リストにある）。
- [ ] 自動確認：1,000 文字のタイトル・改行や制御文字・右から左の文字を含むタイトルで、画面が固まらず、ラベルが画面の外へはみ出さない。
- [ ] `npm audit` で重大・高の指摘が 0 件。

## 段階 2：ストア向けのビルド

  量子化の切り替え（`dtype`）、Worker の WebAssembly のメモリの記録、`setContinuousRender` / `renderNow` などを、ビルドの定数
  （例：`import.meta.env.MODE === "store"`）で囲み、ストア向けのビルドでは静的に消えるようにする。
  開発用の `dist/` と `check:ext` は今までどおり使えるようにする（確認用のビルドとストア向けのビルドを分ける）。

  zip に入るファイルの一覧を出す（ソースマップ・`.DS_Store`・確認用のファイルが入っていないこと）。

## 決めてほしいこと

段階 5・7 で、使う人の判断が必要なもの。判断が出るまで、その項目は作らない。推奨はあくまで提案。

### 1. 星座のメンバーを固定するか（段階 5）
- **A. 今のまま**：保存した検索語で呼び出すたびに検索し直す（pinned / excluded を反映）。ブックマークが増えると、メンバーが変わりうる。
- **B. 保存した時点のメンバーで固定する**：自分で選んだ星だけが星座。増えたブックマークは入らない。
- **C. 固定して、新しく合う星は「新星」として示す**：メンバーは B と同じく固定。保存した検索語に新しく合う星が現れたら、その星座を開いたときに
  新星として光らせ、押すと加えられる。
- **推奨：C**。理由：星座は「自分で名付けたもの」（金の色）なので、知らないうちに形が変わると信頼を損なう（ストアの評価にも響く）。
  一方で、保存した検索の良さ（新しいブックマークに気づける）は、新星として残せる。ハッカソンで見送った「新星」と「自分で選んだ星だけ」を、
  利用者が選べる形で両立できる。保存データの形が変わるので、0.9.x のうちに（1.0 の前に）決めたい。

### 2. ブックマークの削除（片付け）を許すか（段階 7。今の規則 3 に関わる）
- **A. 許さない**：読み取り専用のまま。片付けの機能は作らない。
- **B. 候補を示すだけ**：片付け候補を一覧にし、押すと Chrome のブックマーク マネージャーでその項目を開く。消すのは利用者が Chrome で行う。
- **C. 拡張機能の中で削除できる**：確認と「元に戻す」付きで削除する（規則 3 を変える）。
- **推奨：B（1.0 の後に C を検討）**。理由：ブックマークを消せる拡張機能は、事故が起きたときの損害が大きく、審査と利用者の信頼の両方で
  説明の負担が大きい。B なら規則 3 を変えずに、片付けの価値（候補を見つける）の大半を届けられる。C に進むのは、B の利用状況と要望を見てから。

### 3. 新しいタブ版をどう出すか（段階 7）
- **A. 出さない**：今の「アイコンを押すと専用のタブ」のまま。
- **B. 同じ拡張機能で新しいタブを置き換える**：manifest の `chrome_url_overrides` を足す。入れた人全員の新しいタブが置き換わる
  （設定で切り替えられない。manifest で決まるため）。
- **C. 別の拡張機能（「ブクスペ 新しいタブ」）として出す**：同じコードから別のビルドを作る。新しいタブを置き換えたい人だけが入れる。
- **推奨：1.0 では A、需要があれば C**。理由：B は今の利用者の新しいタブを一斉に奪うので、評価を下げやすく、ストアの審査でも
  「単一用途」の説明が難しくなる。C なら置き換えを望む人だけが選べる。ただし、新しいタブは開くたびに速く表示する必要があり、
  モデルの読み込み（約 0.8 秒）と WebGL の初期化の負担を測ってから決めたい。

### 4. ブックマークが多い人の対象範囲（段階 5）
- **A. すべてを対象にする**：今のまま。5,000 件で初回に約 5.4 分。
- **B. 最初に対象のフォルダを選ぶ**：初回に、星にするフォルダを選ぶ（既定はすべて）。後から変えられる。
- **C. 件数が多いときだけ、最近使ったものから順に計算する**：先に最近の星を出し、残りは裏で続ける。
- **推奨：A を基本に C を足す**。理由：選ぶ手間を増やさずに、最初の星空を早く出せる。B は「使わないフォルダを隠したい」という別の要望として、
  限定公開の声を聞いてから決める。

### 5. 英語対応の範囲（段階 7）
- **A. 画面の文言とストアの掲載文だけ**：埋め込みのモデル（多言語）はそのまま。
- **B. 英語の利用者向けに、英語に強いモデルも選べるようにする**：モデルの切り替えと、それぞれの計算済みを持つ。
- **推奨：A**。理由：今のモデルは多言語で、英語の検索語でも使える。モデルを増やすと、容量・権限・確認の手間が倍になる。
  英語での検索の正解数を、既存の 9 語と同じ形で測ってから、不足があれば B を検討する。

### 6. データの管理とバックアップ（段階 5）
- **A. 書き出し・読み込み（JSON ファイル）だけ**：星座と設定を利用者がファイルで持つ。
- **B. A に加えて、Chrome の同期（`chrome.storage.sync`）で星座を別の PC と同期する**。
- **推奨：A**。理由：同期は容量の上限が小さく（全体で約 100 KB）、星座のメンバー（ブックマークの id）は PC ごとに違うので、
  そのままでは同期しても意味が通らない。書き出しは、ブックマークの id ではなく URL で持つようにして、別の PC でも読み込めるようにする。

### 7. 問題を報告する窓口（段階 4・5）
- **A. GitHub の Issues**：報告の下書き（版・ブラウザ・件数）を作って、Issues の新規作成を開く。GitHub のアカウントが要る。
- **B. Google フォームなどの外部のフォーム**：アカウントが要らない。外部のサービスに報告の内容が渡る。
- **C. メール**：`mailto:` で下書きを作る。
- **推奨：A と C の両方**。理由：どちらも利用者が内容を見てから自分で送るので、規則（利用者のデータを外部に送る処理を書かない）に反しない。
  B は、フォームのサービスのプライバシーポリシーをこちらの説明に含める必要があり、手間の割に得るものが少ない。
  報告の窓口として使うメールアドレスを決めてほしい。

### 8. 3D 描画（WebGL）が使えない環境（段階 5）
- **A. 案内だけ出す**：理由と対処を表示する。
- **B. 平面（2D）の簡易表示を作る**：WebGL なしでも地図と検索だけは使える。
- **推奨：A**。理由：WebGL が使えない環境は少なく、B は描画を二重に持つことになり、確認の手間が大きい。
  限定公開で、案内が出た報告がどれくらいあるかを見てから B を検討する。

### 9. モデルの重みの取り方（段階 2）
- **A. 今のまま Hugging Face から取得する**：権限を実際に使う URL に絞る。配布物は約 28 MB。
- **B. 配布物に同梱する**：外部との通信が無くなり、`host_permissions` も要らなくなる。配布物が約 160 MB になる。
- **推奨：A**。理由：配布物の大きさは更新のたびに全員のダウンロードに効く。取得は初回だけで、送るのは HTTP の要求だけ（ブックマークは送らない）。
  ただし、Hugging Face 側の配信が変わると動かなくなるおそれがあるので、段階 2 で取得先を確かめる確認を置き、変わったときに気づけるようにする。
  「外部と一切通信しない」ことを売りにしたい場合は B。

### 10. フォルダの自動星座をどう作るか（段階 7）
- **A. すべてのフォルダを自動で星座にする**。
- **B. 利用者がフォルダを選んだときだけ、そのフォルダを星座にする**。
- **推奨：B**。理由：フォルダが多い人の画面が銀色の線で埋まり、自分で名付けた星座（金）が目立たなくなる。
  選んだフォルダだけにすれば、「フォルダ＝自分で決めた分類」を星図の上で見る、という用途に絞れる。
